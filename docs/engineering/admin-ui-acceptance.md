## Backup, version upgrade and rollback

The current suite adds a fifth probe for the [user guide](../user-guide.md): use the installed theme's native Download action, retain that archive in memory, overwrite the active theme with a disposable `0.1.1-qa-upgrade` variant, then overwrite it again with the downloaded 0.1.0 backup. The QA variant has distinct template/CSS markers and is never written into the release ZIP or published as a theme release. Ghost 5 exposes its row menu as **Menu**; the modern screen also exposes a menu trigger. Locators follow the observed native controls; response/state assertions are shared.

Both overwrites require exactly one real POST 200 containing the selected bytes, with no activation or deletion write. At each stage the native installed list and backend must show one active entry with the intended version. Frontend CSS bytes and template markers must match that stage; home, public report and the canonical fixture page must render. A digest of selected publication settings and all fixture post/page content, access and template fields must remain unchanged. Signed-out requests to members, paid and tier-only reports must still exclude their protected body markers. Only the digest is recorded, not raw settings/content responses.

`admin-ui.json` includes backup filename/hash, synthetic upgrade hash, per-stage version/state/frontend results and the publication digest. Screenshots retain both version states and the native download menu. This covers theme-file rollback, not a Ghost server/database rollback, custom-theme migration, CDN behaviour, a complete backup or authenticated member access at every stage. The original permission matrix remains separate. Historical four-probe results below do not validate this added case; use the exact current-head CI results.

| Probe | Required evidence |
| --- | --- |
| First installation | Open the official theme-management screen, click Upload theme, select the actual built ZIP in its file input, observe a real browser POST 200 and success dialog, click the native activation button and observe a real PUT 200. The installed row must show the packaged version and Active; backend readback must show one matching active theme. |
| Cancel | Cancel the upload modal before selecting a file, then select the same ZIP and cancel the native overwrite confirmation. No theme POST/PUT/DELETE may occur; the original active name/version stays intact after reload. |
| Confirm repeat upload | Select the same ZIP, confirm Overwrite and observe exactly one real POST 200. The active state/version remain and only one installed entry exists; an already active theme must not trigger another activation request. |
| Invalid ZIP | Upload a valid ZIP container containing only synthetic package metadata, deliberately missing required templates. Real Ghost must return 422, the UI must identify the missing index.hbs and allow closing the error. The invalid theme must not be installed or replace the active release. |

Successful upload requests must contain the exact selected archive bytes. No theme mutation response is mocked or sent through the read-only observation helper. The browser then opens home, a public report and the newly seeded page's canonical path; the served screen.css must match the release payload hash and fixture content must render. Backend GETs only confirm resulting state. All external network access, payment endpoints and third-party marketplace downloads remain blocked; no external account, credential or service is created. Requests specifically to the font provider's `https://fonts.bunny.net/css` stylesheet path receive an empty local CSS response, so this offline browser uses system font fallbacks. This is recorded explicitly and does not validate remote fonts or custom-font visual rendering.

`admin-ui.json` records the ZIP hash/package version, UI request paths/methods/statuses, selected-archive byte matches, resulting theme metadata and strict outcomes. On failure it includes only fixture-visible headings/buttons and frame path names for diagnosis. Screenshots show installed version, overwrite confirmation, invalid-template feedback and frontend pages. The OS-native file dialog itself, theme code editor, third-party marketplace installation and login/security configuration are outside this scope.
